# USB/JTAG runtime and recovery

## Interfaces and tool ownership

The observed composite USB device has CDC control (interface 0), CDC data (interface 1), and vendor JTAG (interface 2). OpenOCD's `board/esp32c3-builtin.cfg` uses the Espressif USB JTAG adapter. The identified TAP was `0x00005c25`; the core reported XLEN 32 and `misa=0x40101104`.

`start_debug.py` starts OpenOCD with Tcl RPC on `127.0.0.1:16666`, telnet disabled, and GDB disabled unless `--gdb-port` is supplied. `--reset` requests one CPU reset after attachment. A unique USB descriptor serial selects the device; multiple connected badges require explicit selection.

The Python client speaks OpenOCD Tcl RPC: UTF-8 command text terminated by byte `0x1a`. It wraps commands in Tcl `catch` and checks the result. `read_memory` and `write_memory` operate on aligned 32-bit words. Firmware commands and hardware commands are different layers: the pin finder exposes no useful USB application command shell, but JTAG accesses the running CPU directly.

Only one Python hardware owner is permitted at a time through a nonblocking OS file lock. OpenOCD itself must also be the only process claiming the JTAG interface. Close esptool/other debuggers before starting it. The lock is scoped to user and Tcl port; it cannot prevent unrelated third-party programs from taking the physical USB device.

## GPIO registers used

| Address | Register |
|---:|---|
| `0x60004004` | GPIO output latch |
| `0x60004008` | Output write-one-to-set |
| `0x6000400c` | Output write-one-to-clear |
| `0x60004020` | Output enables |
| `0x60004024` | Enable write-one-to-set |
| `0x60004028` | Enable write-one-to-clear |
| `0x6000403c` | Input levels |
| `0x60004074 + 4*pin` | Pad configuration; bit 2 is open drain |
| `0x60004554 + 4*pin` | Output matrix; `0x280` selects GPIO latch and software output enable |
| `0x60009004 + 4*pin` | IO mux; function 1, input enable bit 9, pull-up bit 8, pull-down bit 7 |
| `0x600c0008` | CPU clock divider/PLL configuration |
| `0x600c0058` | System clock source |

The pin context saves mux, pad, matrix, output latch, and output enables, disables relevant outputs while reconfiguring, applies initial levels, and restores only the owned bits. I²C uses open drain. It rejects reserved GPIO11–19. Unrelated GPIO output bits are not overwritten wholesale.

```sh
python esp_control.py gpio
python esp_control.py read32 0x6000403c
python esp_control.py cpu
```

`write32 ADDRESS VALUE` is an explicit advanced primitive. It does not infer whether an arbitrary address is appropriate. Avoid eFuse/flash-control/watchdog/power-management writes without their exact documented sequence and purpose. No eFuse write routine is provided.

## Temporary RAM helpers

Fast display/LED output cannot be generated by round-tripping every edge through host USB. `ram_io.py` uses small hand-assembled RV32I helpers:

- Code scratch: `0x40381000`, at most 512 bytes of existing IRAM.
- Data scratch: `0x50001000`, at most 512 bytes of RTC RAM.
- Before any replacement, hash 512 bytes of IRAM and require SHA-256 `041ae4f5dbd98e534d9781d1395909c3b77885bc3e3ec3bd24ddf59948a8e2fc`.
- Save overwritten code/data and every register the helper modifies, plus PC/debug/trap state.
- Disable machine interrupts, configure breakpoint behavior, run a bounded helper, and require the final `ebreak` PC.
- Restore scratch bytes and registers and verify code restoration before allowing the original program to resume.

This is a **firmware-specific scratch strategy**, not a general allocator and not a universal plugin for any ESP32-C3 application. Another firmware may use the memory differently or have DMA/peripheral activity that makes it unsuitable. The guard is intentional. A native application driver is the long-term route for continuous operation.

The helper assembler and generated branches are tested with Capstone. Store instructions target only GPIO set/clear registers. The LED payload in RTC memory is GRB data; it is not executed there. There are bounded pixel/payload sizes and no unbounded helper loops.

## Important failures discovered during development

1. **RTC execution:** the memory at `0x50001000` accepted data writes, but executing a small helper there trapped with Illegal Instruction under this runtime. Use it for data only in this implementation. This is an observation about the configured runtime, not a claim that ESP32-C3 RTC memory can never execute code.
2. **Cycle counter:** standard CSR `mcycle` (`0xb00`) trapped. Espressif's ESP32-C3 cycle counter is `CSR_PCCR_MACHINE=0x7e2`; using it made the LED helper complete. The source is `rv_utils.h`.
3. **Fresh attachment after ROM-loader reset:** a helper write once returned success but read back unchanged IRAM. No helper was executed. An OpenOCD `reset run` followed by the same write/read restored operation. The exact underlying write/protection behavior was not fully diagnosed. Use `start_debug.py --reset`; readback verification remains mandatory.
4. **Output disappears:** the installed scanner reclaims/reconfigures pins after resumption. Keep it halted during inspection (`--hold`) or use a dedicated standalone firmware later.

The first two experiments caused volatile exceptions/resets. Full flash still matched the original backup afterward. A failed RAM helper is not silently retried at another address or allowed to resume arbitrary code.

## Recovery

Normal Ctrl+C triggers Python `finally` cleanup. The tool cannot guarantee cleanup after USB removal, a host crash, SIGKILL, or loss of the debug link during restoration.

If the tool reports that the CPU was left halted, first inspect the error and restoration result. Once scratch restoration succeeded, reset to the installed image:

```sh
python esp_control.py reset
```

If USB is disconnected, reconnect and restart OpenOCD with `--reset`. If a valid app no longer boots after an intentional future flash, use the ROM loader and the complete private backup; see [forensics.md](forensics.md). Do not use erase-flash as a routine connection fix.

## Host platforms

- **Tested:** macOS on Apple Silicon, Python 3.9, Espressif OpenOCD `v0.12.0-esp32-20260831`.
- **Linux:** pinned amd64/arm64/armhf/armel vendor archives are selectable. Install Espressif's USB udev rule through the host's normal administration process if device permission is denied. Hardware operation here was not tested on Linux.
- **Windows:** pinned x64/ARM64 vendor archives and Python locking code are provided. Use Espressif's driver setup for the JTAG interface while preserving the CDC serial interface. Hardware operation here was not tested on Windows.

The stock ESP32-C3 USB controller provides fixed serial/JTAG functionality, not a general USB HID/OTG endpoint implementation. Button IDs in this package are application codes, not USB HID usages or keyboard scan codes.
